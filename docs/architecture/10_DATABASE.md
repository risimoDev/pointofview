## 1. Назначение документа

Документ описывает модель данных платформы: таблицы, связи, индексы, партиционирование, сжатие, ретеншен, стратегию миграций и известные проблемы производительности.

Источники истины в репозитории:
- `infra/postgres/init.sql` — создание схемы (только на пустой БД);
- `infra/postgres/migrations/*.sql` — изменения схемы;
- `api/db/schema.ts` — типы Drizzle (должны соответствовать SQL вручную).

Раздел 12 разбирает несоответствие между этими источниками — оно является главным долгом подсистемы.

## 2. Выбор СУБД

### 2.1. PostgreSQL 16 + TimescaleDB

Образ: `timescale/timescaledb-ha:pg16`. Включает `timescaledb`, `pgvector`, `uuid-ossp`.

```sql
CREATE EXTENSION IF NOT EXISTS timescaledb;
CREATE EXTENSION IF NOT EXISTS "uuid-ossp";
CREATE EXTENSION IF NOT EXISTS vector;
```

### 2.2. Обоснование

Платформа порождает два класса данных с противоположными профилями:

| Класс | Примеры | Профиль |
|---|---|---|
| Справочные | Тенанты, площадки, камеры, зоны, пользователи, правила | Мало строк, частое чтение, изменяемы, нужны связи и целостность |
| Временные ряды | События, аудит | Тысячи вставок в сутки, неизменяемы, чтение по диапазону времени, ретеншен |

Альтернативы и почему отвергнуты:

| Вариант | Почему не выбран |
|---|---|
| Чистый PostgreSQL | Удаление старых событий через `DELETE` раздувает таблицу, требует `VACUUM`, блокирует. Нет сжатия старых данных |
| PostgreSQL + ClickHouse | Две СУБД: два бэкапа, два узла отказа, распределённые запросы «событие + имя камеры» невозможны без денормализации. Оправдано при миллиардах строк, не при тысячах в сутки |
| InfluxDB / Prometheus | Нет связей и транзакций; справочные данные пришлось бы держать отдельно |
| MongoDB | Нет реляционной целостности; `jsonb` в PostgreSQL закрывает потребность в гибкой схеме |

TimescaleDB — это **расширение** PostgreSQL, а не отдельная СУБД. Это ключевой аргумент: одна СУБД, один диалект, один бэкап, один узел отказа, при этом гипертаблицы дают партиционирование, сжатие и мгновенное удаление старых данных.

`pgvector` создаётся заранее: ни одного столбца типа `vector` в схеме нет. Задел под поиск по архиву (CLIP + pgvector, [06_AI_ENGINE.md](06_AI_ENGINE.md), 8.2). Задел бесплатен — расширение уже в образе.

### 3.2. Иерархия владения

```
tenant → site → camera → zone
                      └→ archive_segment
```

Каждый уровень — `ON DELETE CASCADE`. Удаление тенанта удаляет всё, включая события.

Это осознанно и опасно одновременно: удаление тенанта необратимо уничтожает всю его историю. При отсутствии резервных копий ([02_INFRASTRUCTURE.md](02_INFRASTRUCTURE.md), I-01) одна ошибка администратора уничтожает данные клиента.

*Рекомендация:* мягкое удаление тенанта (`deleted_at timestamptz`) вместо физического. Каскад оставить для внутренних сущностей (зоны при удалении камеры), но не для тенанта.

### 3.3. Перечисления

| Тип | Значения | Расхождение |
|---|---|---|
| `tenant_mode` | `cloud`, `onpremise` | — |
| `camera_source` | `rtsp_pull`, `srt_push`, `file` | `srt_push` не делает того, что обещает ([05](05_CAMERA_CONNECTION.md), 6.1) |
| `camera_status` | `online`, `offline`, `error` | **`error` не используется никогда** |
| `zone_kind` | `counter`, `desk`, `shelf`, `queue`, `forbidden`, `required_ppe` | **`required_ppe` без обработчика** |
| `event_type` | 11 значений (см. ниже) | — |
| `event_severity` | `info`, `warn`, `critical` | — |
| `user_role` | `super`, `admin`, `manager`, `operator` | `manager` и `operator` практически не различаются |
| `feature_kind` | `ppe`, `face_id`, `shelf`, `repack`, `queue`, `crowd`, `counter`, `reid` | **`ppe`, `face_id`, `queue` без реализации** |
| `notification_status` | `pending`, `sent`, `failed` | `pending` не используется: статус ставится по факту |

`event_type`:
```
zone_entry | zone_exit | zone_violation | queue_alert | ppe_violation |
repack_event | shelf_violation | crowd | unknown_person |
camera_offline | camera_online
```

`unknown_person` и `ppe_violation` не порождаются ничем.

**Мёртвые значения перечислений — системная проблема, а не мелочь.** Владелец видит в интерфейсе тип зоны `required_ppe`, создаёт её и не получает поведения. Каждое такое значение — обещание, которое продукт не выполняет.

*Рекомендация:* либо реализовать, либо скрыть в интерфейсе с пометкой «в разработке» (модель «каталог в разработке» уже принята для профилей организаций). Удалить значение из перечисления PostgreSQL нельзя без пересоздания типа, поэтому скрытие в интерфейсе — практичный путь.

### 3.4. Почему `app_user`, а не `user`

`user` — зарезервированное слово PostgreSQL (`SELECT user` возвращает текущего пользователя). Таблица потребовала бы кавычек в каждом запросе. Комментарий в схеме это фиксирует.

### 3.5. Роль `jsonb`

`jsonb` используется в 9 столбцах и является главной точкой расширения без миграций.

| Столбец | Содержимое | Валидация |
|---|---|---|
| `tenant.settings` | Произвольное | **Нет** |
| `camera.config` | `frame_skip` | Частично (`CameraConfig` pydantic) |
| `zone.polygon` | `[[x,y],...]` | Zod в API |
| `zone.config` | `dwell_seconds`, `cooldown_seconds`, `ignore_staff` | **Нет** |
| `zone.schedule` | `active_from/to`, `all_from/to` | **Нет** |
| `event.bbox` | `{x1,y1,x2,y2}` | Zod при приёме |
| `event.meta` | Тип-специфично | **Нет** |
| `alert_rule.conditions` | `min_severity` | Частично при чтении |
| `alert_rule.channels` | `[{type, ...}]` | Zod при доставке |
| `tenant_feature.config` | Пороги модулей | **Нет** |
| `system_setting.value` | Значение | `SETTING_DEFS` при записи |

Компромисс: гибкость против гарантий. `meta` позволила добавить `dwell_sec`, `global_id`, `staff`, `count`, `change` без единой миграции — это большая практическая ценность. Цена: содержимое известно только из кода производителя.

*Рекомендация:* валидировать `zone.config` и `tenant_feature.config` схемами Zod на входе в API. Обоснование: сейчас опечатка `dwell_second` вместо `dwell_seconds` принимается молча, и зона не алармит без объяснения причины. Это класс ошибок, который владелец не сможет диагностировать. Для `event.meta` валидацию вводить не нужно — она специфична по типу и меняется чаще всего.

## 4. Гипертаблицы TimescaleDB

### 4.1. Что является гипертаблицей

```sql
SELECT create_hypertable('event', 'ts_start', chunk_time_interval => INTERVAL '1 day');
SELECT create_hypertable('audit_log', 'created_at', chunk_time_interval => INTERVAL '7 days');
```

| Таблица | Колонка | Интервал чанка | Обоснование интервала |
|---|---|---|---|
| `event` | `ts_start` | 1 день | Ретеншен и запросы — по суткам; типовой запрос «за день» попадает в один чанк |
| `audit_log` | `created_at` | 7 дней | Записей на порядки меньше; суточные чанки дали бы множество почти пустых |

Правило TimescaleDB: чанк должен помещаться в память вместе с индексами (ориентир — четверть RAM на активные чанки). При текущих объёмах (тысячи событий в сутки) суточный чанк — доли мегабайта, что даже мелковато. Интервал выбран под удобство ретеншена, и это оправданно.

### 4.2. Составной первичный ключ и его последствия

```sql
PRIMARY KEY (id, ts_start)   -- partition column must be in PK
```

Требование TimescaleDB: колонка партиционирования обязана входить в любой уникальный индекс. Иначе уникальность нельзя обеспечить без проверки всех чанков.

**Следствие, определяющее две другие таблицы:** `event.id` сам по себе **не уникален** с точки зрения ограничений, поэтому **на него нельзя сослаться внешним ключом**.

Это зафиксировано комментариями в схеме и объясняет:
- `notifications.event_id` — без FK;
- `event.resolved_by` — без FK на `app_user` (здесь причина иная — недосмотр);
- предлагаемая `incident_event.event_ts` рядом с `event_id` ([09_WORKFLOW_ENGINE.md](09_WORKFLOW_ENGINE.md), 5.2).

**Скрытая проблема производительности.** Запрос по одному `id` без метки времени:

```sql
SELECT * FROM event WHERE id = '...';   -- сканирует ВСЕ чанки
```

PostgreSQL не может отсечь партиции, потому что в условии нет `ts_start`. При 90 днях ретеншена это 90 чанков.

Это реальный путь исполнения: `worker-alerts` и роуты клипов, снапшота и разбора выбирают событие именно по `id`. Сегодня незаметно (данных мало), станет заметно при росте.

*Рекомендация:* передавать `ts_start` вместе с `id` там, где он известен. `AlertJob` уже содержит `event_id`; добавление `ts_start` в задание позволит запросу отсечь партиции. Для REST-роутов (`/events/:id/clip`) метка времени клиенту известна — она есть в списке событий. Изменение затрагивает схему задания и параметры роутов, но снимает единственную структурную проблему производительности схемы.

### 4.3. Сжатие

```sql
ALTER TABLE event SET (
  timescaledb.compress,
  timescaledb.compress_segmentby = 'tenant_id, camera_id',
  timescaledb.compress_orderby   = 'ts_start DESC'
);
SELECT add_compression_policy('event', INTERVAL '7 days');
```

Чанки старше 7 дней сжимаются автоматически. Ожидаемое сжатие для такого профиля — 10–20 раз.

| Параметр | Значение | Обоснование |
|---|---|---|
| `compress_segmentby` | `tenant_id, camera_id` | Запросы почти всегда фильтруют по тенанту и камере; сегментирование позволяет читать только нужные сегменты |
| `compress_orderby` | `ts_start DESC` | Соседние по времени значения похожи → лучше сжимаются; `DESC` совпадает с порядком чтения |
| Интервал | 7 дней | Свежие данные (аналитика, лента) — несжатые |

**Ограничение, о котором необходимо знать:** сжатые чанки в TimescaleDB **фактически доступны только для чтения**. `UPDATE` по сжатому чанку либо запрещён, либо крайне дорог (в зависимости от версии).

Практическое следствие: `PATCH /events/:id/resolve` для события старше 7 дней **может не сработать**. То же для `UPDATE event SET clip_key` после нарезки клипа по старому событию.

**[Требует проверки на проде]:** воспроизводится ли отказ разбора события старше 7 дней. Это первый кандидат на проверку из всего документа — сценарий реалистичен (владелец разбирает накопившееся раз в месяц), а отказ будет выглядеть необъяснимо.

*Рекомендация при подтверждении:* вынести изменяемые поля (`resolved`, `resolved_by`, `resolved_at`, `clip_key`) из `event` в отдельную обычную таблицу `event_state(event_id, event_ts, ...)`. Гипертаблица остаётся неизменяемой — что соответствует её природе, — а изменяемое состояние живёт там, где его можно менять. Это же согласуется с моделью «события неизменяемы» из [09_WORKFLOW_ENGINE.md](09_WORKFLOW_ENGINE.md), 6.2.

### 4.4. Ретеншен

`api/src/retention.ts`, раз в час:

```typescript
// events: drop whole hypertable chunks past the retention window.
// drop_chunks is the TimescaleDB-native way — instant, frees disk, no bloat.
await db.execute(sql`
  SELECT drop_chunks('event', older_than => ${eventDays}::int * INTERVAL '1 day')
`)
```

`drop_chunks` против `DELETE`:

| Аспект | `DELETE FROM event WHERE ts_start < ...` | `drop_chunks` |
|---|---|---|
| Время | Минуты–часы | **Миллисекунды** |
| Блокировки | Долгие | Только метаданные |
| Раздувание | Мёртвые строки, нужен `VACUUM` | Файл чанка удаляется |
| Освобождение диска | Только после `VACUUM FULL` | Немедленно |
| Гранулярность | Строка | **Чанк целиком** |

Последняя строка — цена решения: удаляется чанк целиком, поэтому `event_retention_days = 90` означает «от 90 до 91 дня» в зависимости от границы чанка. Для ретеншена это несущественно.

Именно `drop_chunks` — главная причина, по которой `event` является гипертаблицей.

**Асимметрия, требующая внимания:** `audit_log` — тоже гипертаблица, но политики ретеншена у неё **нет**. Аудит копится вечно.

*Оценка:* вероятно, это верно. Аудит — доказательная база для службы безопасности заказчика, и его удаление по умолчанию было бы ошибкой. Но решение принято по умолчанию, а не осознанно, и объём никем не контролируется. *Рекомендация:* зафиксировать «аудит не удаляется» как решение и добавить размер `audit_log` в панель `/admin/system`. Если корпоративный заказчик потребует иного срока — вводить настройку.

### 4.5. Непрерывные агрегаты — не используются

TimescaleDB предоставляет `CREATE MATERIALIZED VIEW ... WITH (timescaledb.continuous)` — инкрементально обновляемые агрегаты по временным окнам.

Не используются. Аналитика (`/api/v1/analytics/*`) считает агрегаты запросами на лету.

*Оценка:* при текущих объёмах корректно — преждевременная оптимизация была бы вредна. Но это первый инструмент, к которому следует обратиться, когда `/analytics` начнёт тормозить: почасовые агрегаты событий по тенанту, типу и камере превратят запрос за месяц из сканирования сотен тысяч строк в чтение сотен.

Дополнительно они являются естественной основой правил по агрегату ([08_RULE_ENGINE.md](08_RULE_ENGINE.md), 7.4) и ежедневной сводки.

## 5. Индексы

### 5.1. Реализованные

| Таблица | Индекс | Столбцы | Назначение |
|---|---|---|---|
| `site` | `idx_site_tenant` | `tenant_id` | Площадки тенанта |
| `camera` | `idx_camera_site` | `site_id` | Камеры площадки |
| `zone` | `idx_zone_camera` | `camera_id` | Зоны камеры |
| `event` | `idx_event_tenant_ts` | `tenant_id, ts_start DESC` | **Основной**: лента и аналитика |
| `event` | `idx_event_camera_ts` | `camera_id, ts_start DESC` | Фильтр по камере |
| `event` | `idx_event_type_ts` | `type, ts_start DESC` | Фильтр по типу |
| `alert_rule` | `idx_alert_rule_tenant` | `tenant_id` | Правила тенанта |
| `app_user` | `idx_user_tenant` | `tenant_id` | Пользователи тенанта |
| `app_user` | (unique) | `email` | Вход |
| `audit_log` | `idx_audit_tenant_ts` | `tenant_id, created_at DESC` | Аудит тенанта |
| `archive_segment` | `idx_archive_camera_ts` | `camera_id, started_at DESC` | **Поиск сегментов для клипа** |
| `notifications` | `idx_notification_event` | `event_id` | Журнал доставки по событию |
| `notifications` | `idx_notification_rule` | `rule_id` | По правилу |

`DESC` во всех индексах по времени — не украшение: все запросы читают свежее первым (`ORDER BY ts_start DESC`). Индекс `ASC` заставил бы сканировать в обратную сторону.

### 5.2. Оценка покрытия

| Запрос | Индекс | Оценка |
|---|---|---|
| Лента событий тенанта | `idx_event_tenant_ts` | **Хорошо** |
| События камеры за период | `idx_event_camera_ts` | **Хорошо** |
| События типа за период | `idx_event_type_ts` | **Хорошо** |
| Событие по `id` | **Нет** | **Плохо** — см. 4.2 |
| Необработанные события | **Нет** | Средне: фильтр `resolved = false` после индекса |
| Сегменты архива для клипа | `idx_archive_camera_ts` | **Хорошо** |
| Правила для события | `idx_alert_rule_tenant` | Средне: `event_type` и `enabled` фильтруются после |

**Отбор правил** заслуживает внимания: `WHERE tenant_id = ? AND event_type = ? AND enabled = true` использует индекс только по `tenant_id`. Правил у тенанта единицы — сегодня это неважно. Но запрос выполняется **на каждое событие**, то есть тысячи раз в сутки.

*Рекомендация:* составной индекс `(tenant_id, event_type) WHERE enabled` при росте числа правил. Пока — не трогать: оптимизация без измерения запрещена собственным правилом ([06_AI_ENGINE.md](06_AI_ENGINE.md), 3.5).

**Необработанные события:** ежедневная сводка (`PLAN.md`, блок A) будет запрашивать `WHERE tenant_id = ? AND resolved = false`. Частичный индекс `ON event(tenant_id, ts_start DESC) WHERE NOT resolved` эффективен — необработанных всегда меньшинство. Добавлять вместе с реализацией сводки.

### 5.3. Индексы и сжатие

Индексы на сжатых чанках работают иначе: TimescaleDB хранит сжатые данные по-столбцово, и обычные индексы к ним не применяются. Работают `compress_segmentby`-столбцы (`tenant_id`, `camera_id`) и `compress_orderby` (`ts_start`).

Практический вывод: **запросы по `type` к данным старше 7 дней теряют индекс** `idx_event_type_ts`. Фильтр по типу на сжатом чанке — это распаковка сегмента.

*Рекомендация:* если аналитика по типам за длительный период станет медленной — добавить `type` в `compress_segmentby`. Цена: больше сегментов, хуже сжатие. Решать по измерению.

## 6. Мультитенантность

### 6.1. Модель

Все таблицы, кроме `system_setting`, содержат `tenant_id` прямо или через связь. Изоляция — на уровне приложения: каждый запрос фильтрует по `tenant_id` из JWT.

```typescript
async function ownsCamera(tenantId: string, cameraId: string): Promise<boolean> {
  const [row] = await db.select({ id: camera.id }).from(camera)
    .innerJoin(site, eq(camera.siteId, site.id))
    .where(and(eq(camera.id, cameraId), eq(site.tenantId, tenantId))).limit(1)
  return Boolean(row)
}
```

Камера не имеет `tenant_id` — он достигается через `site`. Это нормализация, но она означает `JOIN` в каждой проверке владения.

### 6.2. Row-Level Security не используется

PostgreSQL поддерживает RLS: политики на уровне строк, применяемые СУБД независимо от запроса.

```sql
-- Не реализовано
ALTER TABLE event ENABLE ROW LEVEL SECURITY;
CREATE POLICY tenant_isolation ON event
  USING (tenant_id = current_setting('app.tenant_id')::uuid);
```

*Оценка.* Текущая модель работает и проверяема ревью. Но она держится на дисциплине: **один забытый `WHERE tenant_id` — это межтенантная утечка**, то есть худший класс уязвимости для платформы видеонаблюдения.

RLS переносит гарантию с дисциплины разработчика на СУБД: даже ошибочный запрос вернёт только строки своего тенанта.

*Рекомендация:* внедрить RLS как **второй рубеж**, не отменяя фильтрацию в коде. Обоснование: цена — установка `SET LOCAL app.tenant_id` на каждую транзакцию (одно место в клиенте Drizzle) и политики на таблицы; выигрыш — структурная невозможность целого класса уязвимостей. Для корпоративной продажи и любого аудита безопасности наличие RLS — сильный аргумент. См. [13_SECURITY.md](13_SECURITY.md).

Оговорка: `/internal/*` и фоновые процессы (retention, watchdog) работают вне тенанта; им потребуется роль с `BYPASSRLS`.

## 7. Redis как проекция

Analyzer не обращается к PostgreSQL (решение A-03). Данные доставляются проекциями:

| Ключ | Источник | Пишет | Формат |
|---|---|---|---|
| `cameras:{tenant_id}` | `camera` ⋈ `site` | `syncCameras()` | JSON-массив |
| `zones:{camera_id}` | `zone` | `syncZones()` | hash `zone_id → JSON` |
| `features:{tenant_id}` | `tenant_feature` | При изменении | JSON-объект |

Проекция `cameras` включает `site.timezone` как `tz` — денормализация ради того, чтобы анализатор не знал про площадки.

Согласованность — «в конечном счёте»: API пишет проекцию при изменении, анализатор читает раз в 30 секунд. Рассинхронизация возможна при очистке Redis; лечится `POST /api/v1/admin/resync`.

**Обратное направление — исключение из модели:** `reid:staff:{tenant_id}` и `face:staff:{tenant_id}` **не имеют источника в PostgreSQL**. Redis для них — система записи.

*Рекомендация (повторяется в [06_AI_ENGINE.md](06_AI_ENGINE.md), 5.8 и [01_SYSTEM_ARCHITECTURE.md](01_SYSTEM_ARCHITECTURE.md), 10):*

```sql
CREATE TABLE staff_identity (
  id         uuid PRIMARY KEY DEFAULT uuid_generate_v4(),
  tenant_id  uuid NOT NULL REFERENCES tenant(id) ON DELETE CASCADE,
  gid        text NOT NULL,
  name       text NOT NULL,
  embeddings jsonb NOT NULL DEFAULT '[]',       -- до 8 эталонов одежды
  face_embeddings jsonb NOT NULL DEFAULT '[]',  -- до 10 эталонов лица
  photo_key  text,                              -- MinIO
  created_at timestamptz NOT NULL DEFAULT now(),
  UNIQUE (tenant_id, gid)
);
```

Redis становится проекцией по единой модели. Отметки сотрудников попадают в резервную копию PostgreSQL. Устраняется единственное место, где потеря тома Redis означает потерю пользовательских данных.

## 9. Транзакции

### 9.1. Модель

Явных транзакций в коде нет. Каждый запрос Drizzle — автокоммит.

Места, где отсутствие транзакции значимо:

| Операция | Шаги | Риск |
|---|---|---|
| Создание камеры | INSERT camera → SET Redis → POST go2rtc → INSERT audit | Частичное выполнение при сбое |
| Вставка события | INSERT event → PUBLISH → BullMQ add → XACK | Разобрано ниже |
| Отметка сотрудника | HSET staff → поглощение дублей → RPUSH face_enroll | Redis-операции без атомарности |

### 9.2. Вставка события: анализ

```typescript
const eventId = await this.insert(msg)          // 1. PostgreSQL
await this.pub.publish(`events:${...}`, raw)    // 2. Redis PubSub
if (!NO_ALERT_TYPES.has(msg.type)) {
  await alertsQueue.add('notify', {...})        // 3. BullMQ
}
await this.redis.xack(...)                      // 4. XACK
```

Сценарии сбоя:

| Сбой на шаге | Последствие |
|---|---|
| 1 | Dead-letter, XACK. Событие потеряно, но зафиксировано в `events:failed` |
| 2 | Исключение → dead-letter → **событие в БД, но помечено как ошибочное** |
| 3 | То же: событие в БД, алерта не будет, сообщение в dead-letter |
| 4 | Событие обработано, но не подтверждено → **повторная обработка → дубль в БД** |

Сбой на шаге 4 приводит к дублированию: сообщение вернётся в pending и будет обработано снова. Впрочем, `XAUTOCLAIM` не вызывается ([01_SYSTEM_ARCHITECTURE.md](01_SYSTEM_ARCHITECTURE.md), 6.3), поэтому «зависшее» сообщение не переобрабатывается вовсе — то есть теряется. Два дефекта компенсируют друг друга случайным образом.

*Рекомендация:* добавить `XAUTOCLAIM` (что необходимо для надёжности) **вместе с** идемпотентностью вставки, иначе повторная обработка создаст дубли. Идемпотентность достижима естественно: добавить в сообщение `event_uid` (генерируется анализатором) и уникальный индекс `(event_uid, ts_start)` с `ON CONFLICT DO NOTHING`. Эти две работы обязаны выполняться одной задачей — по отдельности каждая делает систему хуже.

### 9.3. Уровень изоляции

Умолчание PostgreSQL — `READ COMMITTED`. Не менялось. Для профиля нагрузки (вставки и чтения по диапазону, почти нет конкурентных изменений одной строки) — корректно.

## 12. Миграции

### 12.1. Действующий механизм

`scripts/update.sh` применяет **все** файлы `infra/postgres/migrations/*.sql` при каждом обновлении через `psql` с `ON_ERROR_STOP=1`. Таблицы версий нет.

Следствие — **жёсткое требование идемпотентности каждой миграции**. Оно соблюдено:

```sql
-- 0001, 0003, 0004
ALTER TYPE feature_kind ADD VALUE IF NOT EXISTS 'crowd';

-- 0002
DO $$ BEGIN
  CREATE TYPE notification_status AS ENUM ('pending','sent','failed');
EXCEPTION WHEN duplicate_object THEN null; END $$;
CREATE TABLE IF NOT EXISTS notifications (...);
CREATE INDEX IF NOT EXISTS idx_notification_event ON notifications(event_id);

-- 0005
CREATE TABLE IF NOT EXISTS system_setting (...);
```

Приём с `DO $$ ... EXCEPTION WHEN duplicate_object` нужен потому, что `CREATE TYPE` не поддерживает `IF NOT EXISTS`.

Плюс подхода: невозможна рассинхронизация «применено / не применено». Минус: неидемпотентные операции (`DROP COLUMN`, миграция данных) невыразимы.

### 12.2. Неиспользуемый механизм Drizzle

`api/db/migrate.ts` использует `migrate(db, { migrationsFolder: './db/migrations' })`. **Каталога `api/db/migrations/` не существует.**

`npm run db:migrate` выведет «Running migrations… Migrations complete» и **не сделает ничего**.

Это ловушка: инженер, доверившийся сообщению об успехе, получит рассогласование схемы и кода.

*Рекомендация (повтор из [03_DEPLOYMENT.md](03_DEPLOYMENT.md), 4.1):* удалить `api/db/migrate.ts`, `drizzle.config.ts` и скрипты `db:generate`/`db:migrate`. Оставить `api/db/schema.ts` как источник типов с явной пометкой, что схема ведётся вручную в SQL. Обоснование: миграции TimescaleDB (`create_hypertable`, `add_compression_policy`, `ALTER TYPE ADD VALUE`) Drizzle не генерирует — сырой SQL нужен в любом случае, а два механизма хуже одного.

### 12.3. `init.sql` не равен `init.sql` + миграции

| Объект | В `init.sql` | После миграций |
|---|---|---|
| `feature_kind` | `ppe, face_id, shelf, repack, queue, crowd, counter` | + `reid` |
| `event_type` | 9 значений | + `camera_offline`, `camera_online` |
| `notifications` | **Есть** | То же |
| `system_setting` | **Есть** | То же |

Примечание: `init.sql` уже включает `crowd`, `counter`, `notifications`, `system_setting` — то есть его правили вслед за миграциями. Но `reid`, `camera_offline`, `camera_online` в нём отсутствуют.

Итог: свежая установка **обязана** применить миграции после `init.sql`. Порядок в [03_DEPLOYMENT.md](03_DEPLOYMENT.md), 3.1 это учитывает, но зависимость нигде не проверяется.

Более глубокая проблема: `init.sql` правят вручную вслед за миграциями, что гарантирует расхождение при первом же пропуске.

*Рекомендация:* свести `init.sql` к минимуму (только `CREATE EXTENSION`) и создавать всю схему миграцией `0000_initial.sql`. Тогда «новая установка» и «обновлённая» — это один и тот же путь по построению, а не по дисциплине. Единственная точка расхождения исчезает.

### 12.4. Синхронизация Drizzle и SQL

`api/db/schema.ts` описывает ту же схему на TypeScript. Соответствие обеспечивается **вручную**.

Расхождение приведёт к ошибкам времени выполнения: Drizzle сгенерирует запрос по несуществующему столбцу.

*Рекомендация:* проверка в CI — поднять пустую БД, применить `init.sql` + миграции, выполнить `drizzle-kit check` или сравнить интроспекцию со схемой. Это единственный способ гарантировать соответствие; при отсутствии CI ([19_BEST_PRACTICES.md](19_BEST_PRACTICES.md)) — приоритетный кандидат на первую же проверку.

### 12.5. Правила изменения схемы

| Изменение | Как |
|---|---|
| Новое значение перечисления | `ALTER TYPE ... ADD VALUE IF NOT EXISTS` + `init.sql` + `schema.ts` + Zod + метки UI |
| Новая таблица | `CREATE TABLE IF NOT EXISTS` + `init.sql` + `schema.ts` |
| Новый столбец | `ADD COLUMN IF NOT EXISTS` + `schema.ts` |
| Новый индекс | `CREATE INDEX IF NOT EXISTS` (**`CONCURRENTLY` на проде**) |
| Удаление столбца | **Только в три релиза**: перестать писать → перестать читать → удалить |
| Миграция данных | **Невозможна** в текущем механизме — требует таблицы версий |

`ALTER TYPE ... ADD VALUE` **нельзя выполнять внутри транзакционного блока** в старых версиях PostgreSQL; в 12+ допустимо, но новое значение недоступно в той же транзакции. Поскольку `psql` выполняет файл без явной транзакции, ограничение не проявляется.

| DB-01 | PostgreSQL + TimescaleDB как единственная СУБД | Расширение, а не отдельная СУБД: один бэкап, один узел отказа, реляционные связи + временные ряды | ClickHouse: две СУБД ради объёмов, которых нет |
| DB-02 | `event` — гипертаблица | `drop_chunks` вместо `DELETE`: мгновенно, без раздувания | Обычная таблица: `DELETE` часами, `VACUUM`, блокировки |
| DB-03 | Составной PK `(id, ts_start)` | Требование TimescaleDB | Нет альтернативы |
| DB-04 | `notifications.event_id` без FK | `event.id` не уникален (следствие DB-03) | FK: невозможен физически |
| DB-05 | Чанк `event` = 1 день | Ретеншен и запросы по суткам | Неделя: удаление грубее |
| DB-06 | Чанк `audit_log` = 7 дней | Записей на порядки меньше | День: множество пустых чанков |
| DB-07 | Сжатие через 7 дней, segmentby `tenant_id, camera_id` | Свежие данные несжаты; сегментирование по фильтрам запросов | Сжимать сразу: аналитика по свежим данным медленнее |
| DB-08 | `audit_log` без ретеншена | Доказательная база; объём мал | Ретеншен: потеря аудита |
| DB-09 | Изоляция тенантов в коде, не RLS | Работает, проверяемо ревью | RLS: следует добавить вторым рубежом |
| DB-10 | Analyzer не читает PostgreSQL | Независимость от БД и её схемы | Прямой доступ: связность |
| DB-11 | `jsonb` для расширяемых полей | `meta` дала 5 новых полей без миграций | Столбцы: миграция на каждое поле |
| DB-12 | `app_user`, не `user` | `user` — зарезервированное слово | Кавычки в каждом запросе |
| DB-13 | Миграции — идемпотентные SQL, применяются все | Невозможна рассинхронизация | Таблица версий: сложнее, но нужна для миграции данных |
| DB-14 | Каскадное удаление по иерархии | Простота | Мягкое удаление: нужно для тенанта |

## 12. Расширение по [REVIEW_BOARD.md](REVIEW_BOARD.md)

**Статус: [План].** Дополнения по итогам ревью (B-11, B-28, B-56).

### 12.1. Шардирование по ячейкам (B-11)

При планке БД шардируется **как побочный эффект ячеек** ([20](20_SCALE_ARCHITECTURE.md), 9.1): каждая ячейка — свой PostgreSQL. Специальное шардирование не требуется — 1000 клиентов дают ~90 ГБ за 90 дней (раздел 8.1), объём не является ограничителем. Ячейки дают изоляцию бесплатно.

### 12.2. Область решения DB-01 уточнена

Решение DB-01 (одна СУБД, не ClickHouse) **остаётся верным внутри ячейки**. Но кросс-ячеистая продуктовая аналитика (по всем клиентам) невозможна на 20 отдельных БД. Уточнение ([20](20_SCALE_ARCHITECTURE.md), 9.3): **TimescaleDB в ячейке; колоночное хранилище (ClickHouse) в control plane** для кросс-ячеистой аналитики, наполняемое через CDC. Триггер пересмотра — появление второй ячейки.

Это не отмена DB-01, а определение его области: он касается **клиентской** аналитики внутри тенанта, не **продуктовой** по всем.

### 12.3. Новые таблицы для планки

Ревью вводит таблицы, отсутствующие в текущей схеме:

### 12.4. Legal hold в ретеншене (B-28)

`api/src/retention.ts` — единственное место автоудаления. Проверка `legal_hold` добавляется туда одним условием ([21](21_TENANT_LIFECYCLE.md), 9.6): попавшие в удержание данные (события, архив, клипы) ретеншен пропускает. Приоритет высокий: цена ошибки юридическая — автоудаление доказательства по идущему спору.

### 12.5. Миграции при 20 ячейках (B-56)

Раздел про миграции дополняется требованием совместимости вперёд/назад ([20](20_SCALE_ARCHITECTURE.md), 9.2): при поэтапном выкате ячейки на разных версиях схемы одновременно. Паттерн «расширить → переключить → сузить» становится обязательным.
